# 登入回「後端服務連線逾時」／「旅團後端回應逾時」（GS 5.4.0，2026-11-04）

> 一句話：**唔係 API Key 問題，亦唔需要任何人重設密碼。** 係 Apps Script 做唔完
> 120,000 次 PBKDF2，加上本 repo 兩個放大器（登入掃全表、成功登入再驗一次），
> 加起來就令部分帳號永遠等不到回應。更新 `Code.gs` 到 **GS 5.4.0** 就解決。

---

## 1. 症狀

- 成員／領袖登入，等 45 秒後見到「**連線逾時，伺服器沒有回應，請稍後重試**」或
  「**旅團後端回應逾時，操作可能未完成…**」。
- 但**中央管理帳號（`sheep`）一定入得**。
- 「有時得、有時唔得」；「琴日得、今日唔得」；「頭幾個帳號入得，後面嘅入唔到」。
- 改密碼／忘記密碼偶爾都慢到逾時。

## 2. 一分鐘分辨：唔係 API Key

| 觀察 | 意思 |
| --- | --- |
| `sheep` 入得，但密碼登入逾時 | Key／URL／部署存取權**全部正常**（兩者用同一組 `TROOP_<編號>_BACKEND`＋`_APIKEY` 打同一個 `/exec`） |
| Key 唔對會「快錯」：1–2 秒內回「未授權：缺少 API Key 或有效簽名」 | **永遠唔會**變成 45 秒的「連線逾時」 |
| Vercel → Logs 搵 `troop=1187` | `upstream_timeout`＝後端太慢（今次呢個）；`status=200 success=false`＝後端有答，只係帳密問題 |

所以：**見到「逾時」就唔好改 `TROOP_<編號>_APIKEY`**，改完只會令登記失效，仲多一個問題。

## 3. 真正成因（三個成本疊加）

Apps Script 每次 `Utilities.computeHmacSha256Signature()` 都要過一次 **JS↔Java 邊界**
（實測約 **0.1–0.3 ms**，唔係 Node 嗰種幾微秒）。所以成本要按「**hmac 呼叫次數**」計：

| 路徑 | GS 5.3.0（120,000 次迭代） | 45 秒上限下 |
| --- | --- | --- |
| 新種 `pbkdf2$120000$` 帳號，密碼正確 | 驗證 1× ＋「是否預設密碼」再 1× ＝ **2× ＝ 240,000 次（24–40 秒）** | 邊界，經常逾時 |
| 舊 64-hex 帳號，密碼正確 | 驗證快，但要**即場升級**＝1× 120,000 次 | 12–20 秒，勉強入得 |
| **排第 10 行的帳號** | **逐行掃全表**：每行驗一次 → **10× ＝ 1,200,000 次（120–180 秒）** | ❌ 必定逾時 |
| **密碼錯誤／帳號不存在** | 掃全表 N 次（＋dummy 每次重算） | ❌ 必定逾時 |
| 中央 `sheep` | 0（只驗短效票據） | 正常 |

換句話講，GS 5.2.x–5.3.0 有三個成本同時存在：

1. **迭代次數太高**：120,000 次 × 2（成功登入會為「判斷是不是預設密碼」再驗一次）。
2. **登入掃全表**（本 repo 最嚴重嗰條 bug）：`handleLogin()` 逐行
   `for(i=1;i<data.length;i++){ if(active && verifyPassword(...)) }` —— 每個 active 帳號都跑一次完整 KDF。
   正確密碼要跑到你嗰行先停；錯密碼就係全表 N 次。
3. **dummy 雜湊只 cache 在單次執行**：每次「帳號不存在」都再燒一次。

### 實測數字（`node tests/measure-login-kdf.mjs`，2026-11-04）

腳本用 gas-harness **真實執行** `Code.gs`（不是重寫的 mock），數出每條登入路徑實際做了幾多次
hmac 呼叫。秒數以 scoutbadge 事故回推值 **0.15 ms／次** 換算（`@0.10`／`@0.30 ms` 見腳本輸出）：

| 路徑（13 個帳號的旅團） | 修前 hmac 呼叫 | 修前 @0.15ms | 修後 hmac 呼叫 | 修後 @0.15ms |
| --- | ---: | ---: | ---: | ---: |
| ① 新種 pbkdf2 帳號（第 2 行，密碼正確） | 120,000 | 18.0 s | 10,000 | **1.5 s** |
| ② 舊 64-hex 帳號（含透明升級） | 1,560,000 | 234.0 s ❌ | 10,000 | **1.5 s** |
| ③ 排第 10 行的帳號 | 1,200,000 | 180.0 s ❌ | 10,000 | **1.5 s** |
| ③ 排第 33 行的帳號 | 3,960,000 | 594.0 s ❌ | 10,000 | **1.5 s** |
| ④ 錯密碼 | 3,840,000 | 576.0 s ❌ | 10,000 | **1.5 s** |
| ④ 帳號不存在（dummy KDF） | 240,000 | 36.0 s | 20,000 | **3.0 s** |

修後**任何一條路徑都同「你排第幾行」無關**（恆定 1× KDF），亦唔會隨旅團人數變慢。

## 4. 30 秒驗證（唔需要改任何設定）

1. **本團**：部署 GS 5.4.0 後，喺 Sheet 選單「🔗 旅系統 → **⏱️ 密碼雜湊效能測試**」
   （或 Apps Script 執行 `benchmarkPasswordKdf()`）。輸出直接列出：
   - 1,000／10,000／120,000 次迭代的**即場毫秒數**（用 `Utilities.computeHmacSha256Signature` 原路徑）；
   - 本旅團 `Users` 表四條路徑（①新種 ②舊 64-hex ③第 10／第 30 行 ④錯密碼／帳號不存在）各自幾多毫秒；
   - `✅ PASS`／`❌ FAIL`（任何一條 > 30 秒即 FAIL，因為 proxy 上游上限 45 秒要留緩衝）。
   - 呢個測試**唯讀**，唔會改任何儲存格。
2. **其他旅團（最快）**：Vercel → Logs 用 keyword `slow_password_kdf` 搜。GS 5.4.0 起 proxy 對
   超過 8 秒的密碼類 action（`login`／`changePassword`／`resetPassword`／`forgotPassword` 等）會多寫一行：

   ```
   {"svc":"roverbadge-proxy","result":"slow_password_kdf","troop":"0082","action":"login","duration":12345}
   ```

   唔會記帳號、密碼或 token。另外只要該團仍然回報 GS 5.2.x–5.3.x，
   首頁／登入頁／主頁的「最新版本公告」會直接標紅「**🔴 此版本登入會逾時**」，唔需要逐個問。
3. **個別旅團版本**：開 `https://script.google.com/macros/s/<部署ID>/exec?action=ecStatus`，
   回 `gsVersion`。`5.2.0`–`5.3.x` 即係慢登入版本；`5.4.0` 或以上正常。

## 5. 處理（GS 5.4.0，2026-11-04）

1. 覆寫 `apps-script/Code.gs`（或按畫面「⬇️ 下載 Code.gs」）。
2. Apps Script →「部署」→「**管理部署作業**」→ ✏️ →「版本：**建立新版本**」→ 部署。
   **保留原有 `/exec` 網址**（唔好「新增部署」）。
3. Sheet 選單「🔗 旅系統 → 🔧 **初始化／更新**」按一次（只補缺失工作表／版本標記，不刪資料）。
4. 選單「⏱️ 密碼雜湊效能測試」核實：本版格式應該幾秒內完成。
5. 舊帳號**唔需要任何處理**：下次成功登入會自動改寫成本版格式（密碼不變）。

## 6. GS 5.4.0 改咗乜（逐項對應成因）

| 改動 | 效果 |
| --- | --- |
| `PBKDF2_ITERATIONS` 120,000 → **10,000**；新格式 `pbkdf2$10000$<salt>$<dk>` | 單次 KDF 由 12–20 秒 → 1–3 秒 |
| **驗證一律用雜湊字串自帶的迭代次數**（`parsePbkdf2Hash_`），範圍 1,000–2,000,000 | 舊 `pbkdf2$120000$`、更舊 64-hex 全部照樣登入得，**唔會鎖死任何人** |
| 登入改為 `locateLoginRow_()` **單行定位**（純文字掃描，零 KDF）→ 只驗一次 | 成本與「你排第幾行」「旅團幾多人」脫鈎 |
| 刪走「預設密碼再驗一次」的 KDF；改用**已驗證成功的明文密碼**字串比對 | 成功登入由 2× → 1× |
| 舊雜湊**透明升級**（64-hex 及 `pbkdf2$120000$` → 本版格式，密碼不變） | 舊帳號登入一次即回復 1–3 秒，唔需要重設密碼 |
| dummy 雜湊改用 **CacheService** 跨執行重用 | 「帳號不存在」由 2× → 1× |
| `changePassword` 亦改為單行定位 | 改密碼唔會再掃全表 |
| proxy 新增 `slow_password_kdf` log（> 8 秒的密碼類 action） | 出事時一行認出邊個旅團 |
| 前端版本公告對 GS 5.2.0–5.3.x 標紅「此版本登入會逾時」 | 唔需要逐個問成員「你入唔入到」 |
| `benchmarkPasswordKdf()`＋選單「⏱️ 密碼雜湊效能測試」 | 用真環境數字驗證，唔靠推論 |

## 7. 唔好做嘅事

- **唔好叫用戶重設密碼／清資料／重開帳號**：舊雜湊全部可登入，登入一次會自動升級。
- **唔好改 `TROOP_<編號>_APIKEY`**：與此症狀無關，改完只會令登記失效。
- **唔可以回退成單次 SHA-256**（亦唔好「暫時」改返）：無鹽 = 彩虹表可直接命中、一眼看出誰用同一密碼、破解成本低幾個數量級；
  而登入慢的主因是邊界呼叫次數，不是雜湊強度。
- **唔好單純把 120,000 調低**：`verifyPassword()` 舊版本有 `if(iter<100000) return false`，
  改低之後所有 120k／10k 帳號即刻登入唔到。5.4.0 已改成 1,000–2,000,000 並用雜湊自帶次數。
- **唔好再調高迭代次數**（例如「為咗更安全」改回 120,000）：會再次撞爆 45 秒上限。
  `tests/password-kdf.test.mjs` 有「迭代次數上限 20,000」斷言守住。
- **唔好叫人「再試幾次」**：每次重試都會再排一次長 KDF，Apps Script 同時執行數有限，只會更塞。

## 8. 風險取捨：為何是 10,000 次

本系統存放的資料敏感度低（YMIS／童軍編號、姓名、可選電郵、小隊、進度及徽章），
**沒有電話、身份證、地址**。密碼雜湊真正要保護的是兩件事：

1. **密碼重用**：成員多數是青少年，常用同一個密碼（甚至學校電郵密碼）——雜湊被破解會波及他其他帳號。
2. **管理員帳號權限**：admin／group_leader 可以改全團進度、重設他人密碼、匯出資料。

在這個前提下：

- **10,000 次 ＋ 每戶隨機 16-byte 鹽**已經足夠：配合「連續 5 次錯密鎖 15 分鐘」及反枚舉 dummy KDF，
  線上撞密碼不可行；離線破解的前提是「有人拿到 `Users` 表」，而拿到 Sheet 的人本來就看到全部資料。
- 若日後真的想再加強，正確方向是**把 KDF 搬到 Vercel**（Node 原生 PBKDF2，120,000 次約 40 ms），
  代價是多一次網絡往返與雜湊要經網絡傳遞——以本系統的資料敏感度，現階段唔值得。
